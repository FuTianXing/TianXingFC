# 工具与环境备注

AGENTS.md「修改纪律与执行效率」只留可移植的规则要求；本文件记当前沙箱环境下的具体做法与已知陷阱。**环境一变即重核本文件**，AGENTS.md 的规则不随环境变。

## 一 命令通道的展开陷阱与防线

命令通道先按 shell 语义展开一次字面量，再交给 Python，两层叠加有三类损坏：

| 字符 | 损坏过程 | 症状 |
| --- | --- | --- |
| `$m`、反引号 | shell 变量展开为空串，或命令替换 | 落盘静默缺字 |
| `\t` `\f` `\n` `\b` `\v` `\d` `\x` | shell 折叠反斜杠，Python 再转义成控制字符 | `$\theta$` 变 TAB + `heta`；`\vert` 变 VT + `ert`；`\delta` 变 BS + `elta` |
| `"` | 引号提前终止 | 字符串截断、脚本语法错误 |

**结论**：含 `$`、反引号或反斜杠的文本一律用文件写入接口落盘，不直贴命令通道；落盘后复检 `$` 与反引号计数。

**三道防线**（靠记忆执行不成立：2026-10-22 至 10-23 连续多轮里同一类误解释累计触发六次，每轮都要事后扫控制字符修复）：

- **钩子**：`.githooks/pre-commit` 现挂四道检查，其中 `check_md_control.py` 扫暂存区全部 `.md`，命中控制字符即拒绝提交并报行号与字节值。启用方式 `git config core.hooksPath .githooks`（仓库级已配）。它同时覆盖新文件与存量文件，是唯一不依赖注意力的防线；绕过须 `--no-verify` 并在提交说明写明理由。
- **r-string 三不能**：不能跨行（跨行用 `chr(10)` 拼）；不能含 ASCII 单引号（`\mathbf{k}'` 的撇号会提前终止）；双引号包裹时不能含 ASCII 双引号。含撇号的 LaTeX 用 `chr(39)` 拼接或改全角引号。
- **判别口诀**：见到 `heta`、`imes`、`ext{`、`rac{`、`egin{`、`abla` 这类缺首字母的残部，先查它前面是否有 TAB/VT/FF/BS，不当成拼写错误改字。

## 二 当前环境的具体做法

- **含 LaTeX 或反斜杠的多文件批量修改**：用 Write 落脚本文件（r-string）再执行，禁 `python -c` 与 heredoc 直贴。r-string 只挡 Python 层，挡不住 shell 折叠。同型改动不足十处直接用 Edit 逐处改。
- **Python 解释器**：bash 通道可直接调用 `python`（`/d/Program Files/python313/python`，3.13.11，2026-10-24 复测有）；PATH 再变时走 PowerShell 通道的 `python`。
- **删除临时文件**：bash 通道 `rm -f` 可用（2026-10-24 实测）；`Remove-Item` 在当前策略下被拒。删除前确认目标留在 `_tools/` 内。
- **含 `$` 或反引号的文本写入**：一律 Write 或 Edit 工具（AGENTS.md 2026-10-23 起的硬约束）。
- **工具默认行为与预期不符时用开关解决**：`Select-String` 读 UTF-8 无 BOM 文件加 `-Encoding UTF8`；`git status` 的非 ASCII 路径加 `-c core.quotepath=false` 显示中文。

## 三 两类易错的环境事实

- **终端中文乱码源于字节截断**。禁用 `cut -cN`、`head -cN` 处理中文：按字节计数会把中文切在字符中间，宿主以 GBK 重解整个缓冲区，症状是整段中文同时乱码而 ASCII 完好。改用 `sed -n 'Np'`、`head -n`、Python 字符切片或 Read/Grep 工具。乱码文本不得转写，中文标题与术语一律用 Grep/Read 重取核对。
- **输出被截断的识别**。单行超 2000 字符会被读取工具截断并标 `[truncated]`，取完整长行用 `sed -n 'Np'` 或 Python。

## 四 跨文档同步类任务的做法细节

本节承接 AGENTS.md 的「多文件同步类任务清单先行」与「跨文档任务不攒批」两条。实测样本是 2026-10-24 一次弹性本构线口径同步：一份报告改名、一处门槛数值的档位口径全库同步、一处线状态分层，共触达十四份文档，耗时四小时，其中判断该改什么不足半小时。损耗全在下面三处。

**其一，锚点凭记忆写，脚本 assert 一失败整文件零落盘。** 同一批改动先后写了六个 `sync36` 脚本、四个 `finalize_796` 脚本、三个 `finalize_802` 脚本来回试错。成因两层：锚点取自内存而非文件当前文本，自己早前改过的段落必然改不动；脚本在第三处锚 assert 退出时前两处已写入，我按内存假设认为全部未落盘而整体重跑。

做法：锚点先用 Python 打印目标行的 `repr` 再从文件里取；未命中的锚记录文件名与原因并继续跑完，收尾统一列未命中清单；跑完用 `git diff --numstat` 与 `git diff --ignore-cr-at-eol --stat` 核实每个文件的实际改动行数再定重跑范围。脚本内匹配用字面量 `in` 加切片替换，不用正则。

**其二，攒批期间被并行会话卷走暂存区。** 九份文件改完再一次性 `git add`，其间他人连续三次提交共享 index，我的改动随他人提交入库、提交号归属他人。其中一份档案页有四个 hunk 且仅一个是我的（余三处是他人脚本改名），`git apply --cached` 单 hunk 补丁打不上，因工作区与 HEAD 的同名行已被他人提交改写。

补救手法即索引手术，实测耗时远超逐份提交：`git show HEAD:<路径>` 取行数组，只把自己那一行换成工作区当前行，`git hash-object -w --stdin` 造 blob，`git update-index --cacheinfo <mode>,<sha>,<路径>` 装回。

两个边界。`git restore --staged` 会把 index 整体退回 HEAD、抹掉他人正在暂存的内容，用完须把他人 blob 再装回去。提交后若 `git diff --cached` 仍报差异而 `git diff --numstat HEAD` 为空，属 stat 未刷新，对该文件再 `git add` 一次（内容不变）使 index 与 HEAD 一致，否则他人下次提交会把自己那行回退。

**其三，命令通道与引号的三个陷阱。**

- 含 `$` 的正则不能走 `python -c`：shell 先吃掉反斜杠，`r'对门槛 \$36\.4282\$'` 变成 `\6`，报 `re.PatternError: invalid group reference 6 at position 14`。含 `$` 的匹配一律写成脚本文件。
- `git add` 的路径含 `$` 必须用单引号：双引号或不加引号时 `$K` 被展开为空，报 `FileNotFoundError`，容易被误判为文件不存在。
- 自检脚本扫「本次新增内容」须用 `difflib.SequenceMatcher.get_opcodes()` 逐字符提取插入片段再匹配；直接对 `git diff` 的新增行匹配会把他人历史行一起报出，按整行对齐还会把上下文旧行错算进新增区间。合法的 `\vert` 与 `[[名\|别名]]` 不是裸竖线，判裸竖线前要先去掉已转义竖线。
