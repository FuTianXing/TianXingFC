# 工具与环境备注

AGENTS.md「修改纪律与执行效率」只留可移植的规则要求；本文件记当前沙箱环境下的具体做法与已知陷阱。**环境一变即重核本文件**，AGENTS.md 的规则不随环境变。

## 一 命令通道的展开陷阱与防线

命令通道先按 shell 语义展开一次字面量，再交给 Python，两层叠加有三类损坏：

| 字符 | 损坏过程 | 症状 |
| --- | --- | --- |
| `$m`、反引号 | shell 变量展开为空串，或命令替换 | 落盘静默缺字 |
| `\t` `\f` `\n` `\b` `\v` `\d` `\x` | shell 折叠反斜杠，Python 再转义成控制字符 | `$\theta$` 变 TAB + `heta`；`\vert` 变 VT + `ert`；`\delta` 变 BS + `elta` |
| `"` | 引号提前终止 | 字符串截断、脚本语法错误 |

**结论**：含 `$`、反引号或反斜杠的文本一律用文件写入接口落盘，不直贴命令通道；落盘后复检 `$` 与反引号计数。

**三道防线**（靠记忆执行不成立：2026-10-22 至 10-23 连续多轮里同一类误解释累计触发六次，每轮都要事后扫控制字符修复）：

- **钩子**：`.githooks/pre-commit` 现挂四道检查，其中 `check_md_control.py` 扫暂存区全部 `.md`，命中控制字符即拒绝提交并报行号与字节值。启用方式 `git config core.hooksPath .githooks`（仓库级已配）。它同时覆盖新文件与存量文件，是唯一不依赖注意力的防线；绕过须 `--no-verify` 并在提交说明写明理由。
- **r-string 三不能**：不能跨行（跨行用 `chr(10)` 拼）；不能含 ASCII 单引号（`\mathbf{k}'` 的撇号会提前终止）；双引号包裹时不能含 ASCII 双引号。含撇号的 LaTeX 用 `chr(39)` 拼接或改全角引号。
- **判别口诀**：见到 `heta`、`imes`、`ext{`、`rac{`、`egin{`、`abla` 这类缺首字母的残部，先查它前面是否有 TAB/VT/FF/BS，不当成拼写错误改字。

## 二 当前环境的具体做法

- **含 LaTeX 或反斜杠的多文件批量修改**：用 Write 落脚本文件（r-string）再执行，禁 `python -c` 与 heredoc 直贴。r-string 只挡 Python 层，挡不住 shell 折叠。同型改动不足十处直接用 Edit 逐处改。
- **Python 解释器**：bash 通道可直接调用 `python`（`/d/Program Files/python313/python`，3.13.11，2026-10-24 复测有）；PATH 再变时走 PowerShell 通道的 `python`。
- **删除临时文件**：bash 通道 `rm -f` 可用（2026-10-24 实测）；`Remove-Item` 在当前策略下被拒。删除前确认目标留在 `_tools/` 内。
- **含 `$` 或反引号的文本写入**：一律 Write 或 Edit 工具（AGENTS.md 2026-10-23 起的硬约束）。
- **工具默认行为与预期不符时用开关解决**：`Select-String` 读 UTF-8 无 BOM 文件加 `-Encoding UTF8`；`git status` 的非 ASCII 路径加 `-c core.quotepath=false` 显示中文。

## 三 两类易错的环境事实

- **终端中文乱码源于字节截断**。禁用 `cut -cN`、`head -cN` 处理中文：按字节计数会把中文切在字符中间，宿主以 GBK 重解整个缓冲区，症状是整段中文同时乱码而 ASCII 完好。改用 `sed -n 'Np'`、`head -n`、Python 字符切片或 Read/Grep 工具。乱码文本不得转写，中文标题与术语一律用 Grep/Read 重取核对。
- **输出被截断的识别**。单行超 2000 字符会被读取工具截断并标 `[truncated]`，取完整长行用 `sed -n 'Np'` 或 Python。

## 四 跨文档同步类任务的做法细节

本节把 AGENTS.md 的「多文件同步类任务清单先行」与「跨文档任务不攒批」两条展开成四步。实测样本为 2026-10-24 一次弹性本构线口径同步（一份报告改名、一处门槛数值的档位口径全库同步、一处线状态分层），触达十四份文档，耗时四小时，判断该改什么不足半小时，其余时间耗在这四步没做到位。

**步骤一，一次扫全成清单再动手。** 开局用一条搜索把全部「目标文件＋行号＋命中原文」落成清单，再一次执行完。同一批文件分多轮扫属重复劳动，本轮扫了四轮。清单同时要记下不改的三类：已是新口径的产物、命中数为零的文档，以及指出该问题本身的元语句（例如「这句话须带档位」一类）。后两类若误改，会把订正痕迹一并抹掉。

**步骤二，锚点从文件取，不凭记忆。** 写脚本前先用 Python 打印目标行的 `repr`。自己早前改过的段落，凭内存写的锚必然改不动。本轮同一批改动先后写了六个、四个、三个脚本来回试错，全因这条。

未命中的锚要记录文件名与原因并继续跑完，收尾统一列未命中清单，不用 assert 中断整个脚本。中断时前序锚已落盘、后序未落盘，重跑范围须核实文件实际状态，凭内存假设会连环返工。跑完用 `git diff --numstat` 与 `git diff --ignore-cr-at-eol --stat` 核对每个文件的实际改动行数。

同型改动不足十处直接用 Edit 逐处改；超过十处才落脚本，脚本内匹配用字面量 `in` 加切片替换，不用正则。含 `$` 的正则尤其不能走 `python -c`：shell 先吃掉反斜杠，`r'对门槛 \$36\.4282\$'` 变成 `\6`，报 `re.PatternError: invalid group reference 6 at position 14`。

**步骤三，改一份提交一份。** 攒到全部改完再一次性 `git add`，其间他人提交共享 index 会卷走自身改动，提交号归属他人。本轮九份文件攒批，被并行会话连续三次提交卷走。

已被卷走且同一文件混着他人改动时（一份档案页四个 hunk 里只有一个属自己），`git apply --cached` 的单 hunk 补丁打不上，因 HEAD 的同名行已被他人改写。补救即索引手术，实测耗时远超逐份提交：`git show HEAD:<路径>` 取行数组，只把自己那一行换成工作区当前行，`git hash-object -w --stdin` 造 blob，`git update-index --cacheinfo <mode>,<sha>,<路径>` 装回。

索引手术带出两条边界。`git restore --staged` 会把 index 整体退回 HEAD，抹掉他人正在暂存的内容，用完须把他人 blob 再装回去。`git add` 的路径含 `$` 必须用单引号，双引号或不加引号时 `$K` 被展开为空并报 `FileNotFoundError`，容易被误判为文件不存在。

**步骤四，提交后核 stat，自检只扫本次插入片段。** 若 `git diff --cached` 仍报差异而 `git diff --numstat HEAD` 为空，属 stat 未刷新，对该文件再 `git add` 一次（内容不变）使 index 与 HEAD 一致，否则他人下次提交会把自己那行回退。

扫「本次新增内容」须用 `difflib.SequenceMatcher.get_opcodes()` 逐字符提取插入片段再匹配。对 `git diff` 的新增行按整行对齐匹配会把上下文旧行错算进新增区间，本轮即报出三处他人旧行。合法的 `\vert` 与 `[[名\|别名]]` 不属裸竖线，判裸竖线前要先去掉已转义竖线。
